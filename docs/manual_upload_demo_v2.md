# 研发协作与发布响应规范（手动上传测试版 v2）

## 一、文档目的

本文档用于演示企业知识库系统的手动上传、解析、切块、权限控制、引用式问答、版本对比和派生结果生成能力。与 v1 相比，本版补充了发布风险分级、客户沟通节奏、回滚触发条件、值班交接模板和安全例外关闭要求，便于测试系统是否能正确识别“新增、删除、修改”的条款差异。

为了方便测试，本版依旧保留了研发协作、版本发布、事故响应、值班安排、安全例外、FAQ 沉淀等多个内部知识场景，但对若干关键阈值、责任表述和审批要求做了调整。上传 v2 后，建议重点测试以下问题：第一，比较 v1 与 v2 的差异摘要；第二，围绕“高风险发布”“客户事故沟通”“安全例外到期处理”等新增内容发起问答；第三，验证 citation 是否来自最新版本；第四，验证待办提取是否能抓到新增的执行要求。

## 二、适用范围

本文档适用于平台研发团队、SRE 值班人员、项目经理、组长以及参与线上发布和故障处置的协作成员。对于普通员工，本文件主要用于查询发布纪律、事故升级原则和值班交接规范；对于组长和管理员，本文件还用于理解升级决策、放量条件、跨团队协同和审计要求。

本文档仍不替代正式的安全管理制度、员工手册或事故分级规范。若本文档与正式制度冲突，应以正式制度为准；若存在未覆盖场景，应联系文档 owner 或管理员确认。本文档中的流程说明仅用于内部管理和培训，不得未经批准对外传播。

## 三、发布前检查要求

所有常规版本发布必须至少提前一个工作日完成发布申请登记，并在发布说明中明确版本号、负责人、变更范围、影响范围、回滚方案、观察指标和紧急联系人。与 v1 相比，本版新增要求：对于涉及数据库迁移、计费、登录认证、风控规则、配置中心或流量路由的变更，必须在申请中明确风险级别和审批结论。

发布前检查至少包括以下内容：

1. 确认变更已经通过代码评审，且评审结论可追溯。
2. 确认测试环境已经完成功能验证，并记录核心验证结论。
3. 确认数据库变更脚本已经过演练，具备回退说明。
4. 确认监控、日志、告警和业务指标具备发布后观察条件。
5. 确认值班人员知晓发布时间窗和潜在风险。
6. 确认如涉及前端静态资源刷新，已经明确缓存刷新策略。
7. 确认是否需要客户侧公告、状态页维护或客服预备话术。

对于涉及高风险链路的发布，必须由组长和管理员共同批准。若变更被标记为高风险但未提供可执行的回滚路径，不得进入生产环境。与 v1 不同，本版不再接受“上线后观察再补文档”的做法，发布说明必须在执行前完整提交。

## 四、风险分级与放量策略

本版新增发布风险分级规则，将变更分为低风险、中风险和高风险三类。

- 低风险：无数据库变更、无外部接口兼容性变化、支持快速回滚的小流量服务更新。
- 中风险：涉及关键服务版本升级、依赖组件变更、高并发配置调整或跨服务联动发布。
- 高风险：涉及数据库迁移、认证鉴权变更、核心计费链路、支付路径、风控规则或基础设施权限调整。

低风险变更可一次性完成发布，但仍需至少观察十五分钟；中风险变更必须分批放量，并在每个批次确认核心指标稳定；高风险变更必须采用“灰度 + 观察 + 批准”模式，不得一次性全量上线。与 v1 相比，这一章节是新增内容，可作为版本 diff 的重点测试对象。

## 五、发布窗口与执行纪律

常规发布时间窗调整为工作日 10:00 至 16:30。与 v1 的 17:00 截止相比，本版将常规发布时间窗提前收口，目的是为观察期和回滚预留更充分时间。节假日前一工作日下午 14:00 后原则上不得执行非紧急生产发布。

紧急修复发布允许在非标准窗口执行，但必须满足以下条件：问题已对用户产生明显影响；延迟处理会扩大损失；发布内容已缩到最小修复范围；值班人员和负责人在线；发布后的观察和回滚路径清晰；必要时已通知业务接口人和客服负责人。

发布开始前，负责人应在统一通知渠道发出说明，包括：发布时间、变更内容、风险提示、观察指标、回滚负责人和预计恢复时间。与 v1 相比，本版新增“通知渠道统一模板”要求，避免不同团队使用不同表述造成误解。

## 六、回滚要求

每次生产发布都必须在执行前准备明确的回滚路径。对于无状态服务，应说明回滚所需版本和切换步骤；对于数据库变更，应说明是否可逆、不可逆部分的隔离措施以及业务补偿方式；对于配置变更，应说明回退项和缓存刷新方式。

回滚触发条件也做了更新：若发布后十分钟内核心错误率持续高于基线两倍、支付成功率下降、接口超时大幅增加或关键业务链路不可用，应立即停止继续放量，并优先评估回滚。与 v1 相比，本版把“观察窗口”从五分钟延长到十分钟，但同时要求更明确地对照基线指标判断。

回滚决定不应被视为失败，而应被视为风险控制动作。发布负责人必须在回滚后补充事件记录，包括：触发回滚的指标、判断依据、执行时间、恢复时间以及后续修复计划。本版额外要求：如果同类变更在一个季度内发生两次以上回滚，必须发起流程复盘。

## 七、事故分级与升级路径

生产事故仍按照影响范围和恢复复杂度分为 P1、P2、P3 三个级别，但本版补充了面向客户沟通的升级要求。

- P1：核心业务不可用、支付中断、大面积登录失败、用户数据损坏风险或持续性高错误率。
- P2：重要功能受限、部分用户受影响、存在临时绕过方案但影响持续。
- P3：非核心功能异常、局部问题或影响范围较小的问题。

当事故被判断为 P1 时，组长需要在十分钟内建立事故沟通渠道，并明确事故 owner、技术排查负责人、沟通负责人和记录人。与 v1 相比，本版新增要求：若事故已经影响外部客户，十五分钟内必须给出第一次对外状态更新，即使结论仍在确认中，也要明确“已识别问题、正在处理、下次更新时间”。

## 八、事故处理中的角色责任

事故 owner 负责总体推进，包括：组织排查、分配任务、确认优先级、决定是否回滚、协调依赖团队和更新处理结论。技术排查负责人负责提出定位假设、组织验证、收敛原因范围和推动修复。记录人负责维护时间线，包括告警时间、首次确认时间、关键判断、回滚或修复时间以及恢复验证结果。

组长在事故中的责任，不是亲自处理所有技术细节，而是确保节奏被管理。组长至少需要完成以下动作：

1. 在事故升级后确认 owner 和沟通负责人是否明确。
2. 确认当前影响范围是否已经被识别。
3. 确认业务方和客服是否收到一致版本的信息。
4. 确认是否需要回滚而不是继续冒险修复。
5. 在恢复后要求安排复盘和改进项落地。
6. 当事故持续三十分钟以上时，确认是否需要升级管理层同步。

与 v1 相比，本版增加了第六条，用于强调长时间事故的升级同步责任。

## 九、值班安排与交接要求

值班表必须至少提前一周确认，并明确主值班、备值班、紧急联系人和替班规则。节假日值班需在排班系统中登记，不得只在聊天工具中口头约定。主值班需要保证在值班窗口内可被通知触达，备值班需要在主值班失联或问题升级时及时接管。

每周值班交接应包含以下信息：

1. 当前已知风险项和历史遗留问题。
2. 最近一周的重要发布和未完成观察项。
3. 仍在跟踪的告警抖动、容量风险或外部依赖风险。
4. 特殊客户保障要求或节假日变更。
5. 常用排查看板、日志入口和应急联系人。
6. 当前仍在生效的安全例外及其到期时间。

与 v1 相比，本版新增了第六项，便于把值班交接与安全例外管理串联起来。

## 十、安全例外与风险接受

当某项业务需求在当前时间窗内无法完全满足标准安全基线，但又因业务连续性、供应商依赖、历史兼容或客户交付窗口等原因必须临时上线时，可发起安全例外登记。安全例外不是永久豁免，而是一种有范围、有期限、有责任人的临时风险接受流程。

安全例外登记至少必须回答以下问题：

1. 为什么必须例外。
2. 例外会带来什么风险。
3. 当前有哪些补偿性控制措施。
4. 谁对该风险负责。
5. 什么时候关闭例外。
6. 若到期仍未关闭，谁负责重新评估。

与 v1 相比，本版增加了第六项，并明确要求任何安全例外都必须包含到期时间和复核责任人。若例外到期仍未关闭，系统管理员必须要求重新评估；若补偿性控制措施未按计划落实，应暂停该例外继续生效。

## 十一、复盘与改进

对于面向客户的事故，建议在五个工作日内完成复盘。复盘至少应回答：问题为什么会发生、为什么没能更早发现、为什么现有防护没能阻止影响扩散、处理中的哪些动作有效、哪些动作增加了混乱、还需要补哪些自动化或流程改进。

复盘要聚焦系统改进，而不是简单归因到某个个人“粗心”或“经验不足”。可以从监控、预案、沟通、发布流程、权限配置、数据保护、回滚演练和知识沉淀等角度提出行动项。每条行动项都应明确 owner、截止时间和验收标准。

与 v1 相比，本版新增要求：复盘行动项的默认跟踪周期为两周，若超期未完成，组长需要在周会中说明原因并更新计划。

## 十二、FAQ 沉淀建议

高频被重复提问的问题，建议转写为 FAQ 草稿，至少包括：问题、简短回答、适用范围、来源文档、更新时间和 owner。FAQ 适合解决“节假日安排怎么查”“发布前必须检查什么”“事故升级后组长要做什么”“安全例外需要谁审批”等重复性问题。

FAQ 草稿进入知识库前，应检查以下内容：

1. 回答是否仅基于可追溯来源。
2. 回答是否使用了过度绝对化的措辞。
3. 回答是否适合面向当前读者角色。
4. 是否给出了必要的限制条件和更新时间。
5. 是否明确标出适用版本。

本版新增了第五条，以便测试 FAQ 场景中的版本意识。

2. 常规发布时间窗和节假日前限制有什么变化？

5. 值班交接现在新增了什么内容？
6. 安全例外到期后谁负责重新评估？
7. v1 和 v2 相比，发布和事故流程有哪些关键变化？
